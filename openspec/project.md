# AiotInOne Project Context

## 1. 專案願景

建立一套模組化 AIoT 平台，讓感測器、控制設備、AI 分析與商業流程可以透過共用核心快速組裝成不同產業產品。

第一個產品場景為智慧農業，服務生產端農民、銷售端商家與消費端使用者，並由治理後台統一管理設備、權限、告警、AI 模型與稽核紀錄。

## 2. 核心問題

- 感測資料分散，農民難以即時掌握農場環境。
- 設備控制、告警與 AI 建議缺乏一致流程。
- 生產端、銷售端與消費端資料沒有形成可追溯的產銷鏈。
- AI 建議常與實際設備控制混在一起，存在安全與責任風險。
- 傳統專案需求多留在聊天紀錄，容易產生規格漂移。

## 3. 商業角色

### Producer｜生產端

- 建立農場、田區、溫室與作物批次。
- 註冊感測器與控制設備。
- 查看即時資料、告警、AI 建議與生產預測。
- 建立可供應農產品與追溯資料。

### Merchant｜銷售端

- 查看可供應農產品與預估產量。
- 建立採購需求、供應媒合與庫存規劃。
- 查看批次品質與產地追溯資訊。
- 使用 AI 需求與補貨建議。

### Consumer｜消費端

- 查詢商品、產地、批次與環境摘要。
- 查看季節、新鮮度與料理推薦。
- 建立訂單或關注商品。

### Administrator｜治理端

- 管理帳號、角色、租戶、設備與平台設定。
- 管理告警規則、AI 模型版本、稽核與安全事件。
- 不列入商業三方角色。

## 4. AI 功能範圍

AI 採三者整合：

1. 異常偵測：環境異常、感測器漂移、設備故障跡象。
2. 預測分析：灌溉需求、採收日期、產量、供應與需求。
3. 智慧推薦：農務建議、商家採購建議、消費者商品推薦。

AI 輸出必須保留模型版本、輸入摘要、可信度、產生時間與解釋。AI 建議不得直接成為設備控制命令，除非另有經核准的自動化規格。

## 5. 建議技術棧

- PHP 8.3+
- Laravel 12+
- PostgreSQL 16+
- Redis 7+
- Python 3.12+ / FastAPI
- MQTT / EMQX 或 Mosquitto
- ESP32
- Docker Compose
- Laravel Queue / Scheduler
- PHPUnit 或 Pest
- Pytest

前端採 Blade + Livewire 或 Inertia + Vue 3，須在第一個實作 change 中做成正式決策。

## 6. 架構原則

- 模組化單體優先，避免 MVP 過早微服務化。
- AI 推論與 IoT Broker 保持外部服務邊界。
- Laravel 是權限、商業流程與資料一致性的系統核心。
- MQTT 資料先經 ingestion service 驗證、正規化、去重，再寫入資料庫。
- 高頻原始資料與商業交易資料必須區分保存策略。
- 所有 API 與事件都要有版本與契約。
- 所有控制命令都要可追蹤、可撤銷或安全逾時。

## 7. 規格撰寫約定

- Capability 名稱使用 kebab-case。
- Change 名稱使用動詞開頭的 kebab-case。
- Requirement 使用 `### Requirement:`。
- 強制需求使用 SHALL 或 MUST。
- 每個 Requirement 至少一個 `#### Scenario:`。
- Scenario 使用 GIVEN／WHEN／THEN。
- `openspec/specs/` 只描述已完成且已部署能力。
- 尚未實作的能力只放在 `openspec/changes/<change>/specs/`。

## 8. MVP 邊界

MVP 包含：

- 四類帳號與 RBAC。
- 農場、田區、作物批次與設備管理。
- ESP32 透過 MQTT 上傳溫度、空氣濕度、土壤濕度與光照。
- 即時儀表板、歷史趨勢與門檻告警。
- AI 異常摘要、灌溉建議與基礎產量預測介面。
- 生產端、銷售端與消費端三套入口。
- 農產品批次與基本追溯頁。

MVP 不包含：

- AI 完全自主控制設備。
- 金流與複雜物流。
- 大型多租戶計費。
- 無人機與影像辨識。
- 區塊鏈追溯。
